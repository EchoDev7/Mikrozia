Inside the container or via terminal, the `x-ui` command is your management center. Run it with
no arguments for the interactive menu, or pass a subcommand for a one-shot action.

```bash
x-ui
```

## The `x-ui` management menu

The menu (items `0`–`16`) displays the panel and Xray status at the top:

| #     | Item                                   | What it does                                              |
| ----- | -------------------------------------- | --------------------------------------------------------- |
| 1     | Reset Username & Password              | Set new credentials; optionally disable 2FA               |
| 2     | Reset Web Base Path                    | Reset the web base path                                   |
| 3     | Reset Settings                         | Reset panel settings (your account is preserved)          |
| 4     | Change Port                            | Change the panel port                                     |
| 5     | View Current Settings                  | Show username, port, web base path, cert paths            |
| 6–7   | Show RouterOS Start / Stop Command     | Print RouterOS `/container/start` & `/container/stop` commands |
| 8     | Reload Panel & Restart Xray            | Reload panel web/sub (`SIGHUP`) & restart Xray (`SIGUSR1`) without restarting the container |
| 9     | Restart Xray Only                      | Send `SIGUSR1` to restart only Xray-core inside the container |
| 10    | Check Status                           | Panel, Xray, and MTProto runtime status plus RouterOS autostart command |
| 11    | Logs Management                        | View panel debug log / RouterOS container log commands    |
| 12–13 | Show RouterOS Enable / Disable Autostart Command | Print RouterOS `/container/set ... start-on-boot` & `restart-policy` commands |
| 14    | TLS Certificate Paths                  | Select user-supplied certificate files for the panel; issuance and renewal happen outside the container |
| 15    | RouterOS Network Policy Notice         | Notice on configuring network and firewall in RouterOS    |
| 16    | Database Tools                         | Convert SQLite `.db` ↔ `.dump` & external PostgreSQL guide |
| 0     | Exit                                   | Exit Script                                               |

Some of these options have their own guides: [TLS certificates](/docs/config/ssl-certificates)
(item 14), [Panel settings](/docs/config/panel) (TLS), and [Database](/docs/reference/database) (PostgreSQL).

## CLI subcommands

For scripts and quick actions, `x-ui` accepts subcommands directly:

| Command                    | Action                                              |
| -------------------------- | --------------------------------------------------- |
| `x-ui version`             | Show Mikrozia version                               |
| `x-ui start` / `stop`      | Print RouterOS `/container/start` and `/container/stop` commands (managed on RouterOS) |
| `x-ui restart`             | Reload panel web/sub and restart Xray internally (does not restart the RouterOS container) |
| `x-ui restart-xray`        | Restart only Xray-core inside the running container (`SIGUSR1`) |
| `x-ui status`              | Show Panel/Xray/MTProto status and RouterOS autostart check command |
| `x-ui settings`            | Show current settings                               |
| `x-ui enable` / `disable`  | Print RouterOS `/container/set` commands for `start-on-boot` and `restart-policy` |
| `x-ui log`                 | View debug log                                      |
| `x-ui migrateDB [file]`    | Convert SQLite `.db` ↔ `.dump`                      |

## Updating

In Mikrozia, panel updates are performed exclusively by replacing the Container or Container Image. Legacy in-place self-update scripts (`update.sh`) that ran inside the container have been completely removed to protect the container RootFS and preserve stability on RouterOS.

To update Mikrozia:
1. Pull the new Mikrozia container image tag (e.g. from Docker Hub `majlot/mikrozia`).
2. Stop the current container and recreate it with the new image, reusing the existing persistent mounts (`/etc/x-ui` and `/root/cert`).
3. Start the new container.

Your database, accounts, and certificates in the mounted persistent directories are fully preserved across container updates. Always take a [backup](/docs/operations/backup-restore) before upgrading across major releases.

### Rolling back an image update

If the new image fails validation, keep the container stopped, recreate it with the previous versioned image tag, and reuse the same `/etc/x-ui` and `/root/cert` mounts. The database and certificates are not part of the image. If the new image already migrated the database schema, restore the pre-update database backup before starting the older image; an older panel must never open a newer schema. Image rollback never requires copying data into the image RootFS.

<Callout type="info">
  Mikrozia never modifies its own RootFS at runtime. Container image replacement guarantees a clean, immutable, and reproducible deployment.
</Callout>

For a full container restart from RouterOS Terminal or WinBox, run: `/container/restart [find where comment="[Mikrozia:container] Container"]`.

## Uninstalling

To uninstall Mikrozia in RouterOS:
1. Stop the container: `/container/stop [find where comment="[Mikrozia:container] Container"]`
2. Remove the container instance: `/container/remove [find where comment="[Mikrozia:container] Container"]`

<Callout type="warn">
  Removing the RouterOS container does not automatically delete your persistent mount folders (`/etc/x-ui` and `/root/cert`). Deleting database files and certificates must always be a separate, deliberate, and explicit operator action on the host storage, ensuring zero accidental data loss.
</Callout>
