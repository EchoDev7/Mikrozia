---
title: TLS Certificates
description: Supply and rotate TLS certificates for the Mikrozia panel and inbounds. Mikrozia does not issue or renew certificates inside the container.
icon: ShieldCheck
---

A TLS certificate lets you serve the **panel** over HTTPS (so your login and API
traffic are encrypted) and terminate TLS on **inbounds** (VLESS-TLS, Trojan,
Shadowsocks-TLS, and friends). Mikrozia only **reads** certificate files that you
provide. It does not run an ACME client, certbot, or any other certificate
issuer inside the container.

<Callout type="warn">
  Certificate acquisition and renewal are **user-managed**. Mikrozia never
  downloads or installs certificate tooling at runtime, and never creates or
  changes RouterOS firewall, NAT, or port-forwarding rules. If your validation
  method needs a public port, configure that access yourself in RouterOS.
</Callout>

## Obtain the certificate outside the container

Use the issuance and renewal procedure provided by your certificate authority
on a host you control, then copy the resulting files to the router's persistent
certificate storage. Do not install packages or run certificate installers
inside the Mikrozia container.

A certificate and its private key are usually two files:

- `fullchain.pem` — the certificate plus intermediate chain.
- `privkey.pem` — the private key. Keep it private and never place it in an
  image, a support bundle, or a log.

## Store it on the persistent certificate mount

Create one directory per certificate under `/root/cert` (the container path for
the RouterOS certificate mount):

```text
/root/cert/vpn.example.com/fullchain.pem
/root/cert/vpn.example.com/privkey.pem
```

Both files must exist at their final paths before you configure the panel. This
directory is a persistent mount, so certificates survive container image
replacement and rollback.

## Point the panel at the files

Choose one of these equivalent methods:

- Run `x-ui`, select **`14` — TLS Certificate Paths**, then **`2` — Set
  certificate paths for the panel**.
- Run the CLI directly:

  ```bash
  x-ui cert -webCert /root/cert/vpn.example.com/fullchain.pem \
    -webCertKey /root/cert/vpn.example.com/privkey.pem
  x-ui restart
  ```

- Set `webCertFile` and `webKeyFile` in
  [Panel Settings](/docs/config/panel#tls).

The panel switches to HTTPS only when **both** paths are set and both files are
readable. To clear them, run `x-ui cert -reset`.

## Use the certificate on inbounds

When you enable TLS on an inbound, reference the same certificate and key paths
(or paste their contents) in the inbound's TLS settings. See
[Inbounds](/docs/config/inbounds) and [Transports](/docs/config/transports).
[REALITY](/docs/config/reality) inbounds need **no** certificate at all; they
borrow a real site's TLS.

## Renew and rotate

Renewal happens outside the container, on the schedule you manage. When the CA
issues a new certificate, overwrite the same `fullchain.pem` and `privkey.pem`
files so the panel's stored paths stay valid, then reload the panel:

```bash
x-ui restart
```

`x-ui restart` reloads the panel web and subscription services and restarts
Xray inside the running container. There is no renewal daemon or cron job in the
container, and no certificate is ever fetched automatically.

If you move a certificate to a different path, update the panel settings again
with menu `14` or `x-ui cert`.

<Callout type="info">
  Certificates expire. Monitor expiry with your external issuance tooling and
  replace the mounted files before they lapse; the panel keeps reading the files
  at their configured paths.
</Callout>
