Mikrozia listens on a small set of ports **inside** the container. It never
creates or changes RouterOS firewall, NAT, masquerade, port-forwarding, routing,
or access-control rules, and the image contains no `ufw`, `iptables`, or
`nftables`.

## Ports inside the container

| Port (default) | Purpose |
| -------------- | ------- |
| `2053` | Panel (configurable in Panel Settings) |
| `2096` | Subscription server (if enabled) |
| inbound ports | Every port you assign to an Xray inbound |

The container address in the beginner layout is `172.16.10.2`.

## Network policy is yours

Decide in RouterOS how these ports are reached:

- which interface or address list may reach the panel;
- whether and how an inbound port is forwarded to `172.16.10.2`;
- how the container reaches the internet;
- drop, rate-limit, and logging policy.

Mikrozia documents the required ports but does not automate any of these steps.
Follow MikroTik's RouterOS documentation for firewall, NAT, and routing.

<Callout type="warn">
  Keep management access to RouterOS itself working before you apply any
  restrictive policy. Test from a second session so you do not lock yourself
  out.
</Callout>

## Verify from inside

If a client cannot connect, first confirm the panel and Xray are running inside
the container:

```text
/container/print detail where comment="[Mikrozia:container] Container"
/log/print follow-only where topics~"container"
```

Then confirm your RouterOS policy actually delivers traffic to the container
address and port. See [Troubleshooting](/docs/help/troubleshooting).
