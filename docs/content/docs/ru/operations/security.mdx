Прокси-панель — ценная цель для атак. Несколько уровней защиты дают большой эффект.

## Усиление защиты панели

- Надёжные, уникальные учётные данные и **двухфакторная аутентификация** (TOTP).
- Нестандартный порт панели и длинный случайный базовый веб-путь.
- TLS на панели (напрямую или через [обратный прокси](/docs/operations/reverse-proxy)).
- Встроенный **ограничитель входа** блокирует IP/имя пользователя после 5 неудачных попыток
  за 5 минут (на 15 минут), а панель может направлять собственный исходящий трафик через
  outbound.

Полный чек-лист см. в разделе [Первый вход](/docs/guide/first-login).

## Журнал IP клиентов

Панель записывает исходные IP-адреса, которые наблюдает для каждого клиента, через API
онлайн-статистики Xray (см. [Клиенты](/docs/config/clients)). Это только наблюдение:
контейнер RouterOS не может установить или запустить Fail2ban, `iptables` или `nftables`,
а Mikrozia никогда не создаёт и не изменяет правила брандмауэра RouterOS. Поэтому
ограничение числа одновременных исходных IP на клиента — задача администратора RouterOS.

Сохранённые в прежних версиях значения `limitIp` остаются без изменений. Панель их не
применяет и не сбрасывает, не обнуляет и не переинтерпретирует при обновлении, миграции,
резервном копировании или восстановлении.

## Сетевая политика

Открывайте только те порты, которые действительно используете: управление RouterOS, порт
панели, порт подписки и ваши входящие порты. В Mikrozia нет меню брандмауэра, и она не
поставляет `ufw`, `iptables` или `nftables`; вся политика фильтрации, NAT, проброса портов,
маршрутизации и контроля доступа настраивается администратором RouterOS. См.
[Порты и брандмауэр](/docs/reference/ports-firewall).

<Callout type="warn">
  Перед применением ограничивающей политики убедитесь, что управление RouterOS
  остаётся доступным. Проверяйте из второй сессии, чтобы не заблокировать себе доступ.
</Callout>

## Границы ядра хоста (BBR)

В Mikrozia **отсутствует** меню или переключатель Host Kernel BBR через `sysctl` в `x-ui`:

- RouterOS полностью владеет ядром хоста; контейнер не может устанавливать модули ядра или менять системный алгоритм TCP (`net.ipv4.tcp_congestion_control`, `net.core.default_qdisc`).
- Вызов `sysctl` внутри контейнера не создаёт отсутствующую в ядре поддержку, а настройки Queue или Firewall в RouterOS не заменяют Kernel BBR.
- Реализация BBR в пространстве пользователя для **TUIC**, **QUIC** и **FinalMask** не зависит от ядра хоста и сохранена.
- Параметр Xray sockopt `tcpcongestion=bbr` зависит от ядра и оставлен на отдельный последующий аудит совместимости.

## Поддерживайте актуальность

Панель, Xray, sidecar-компоненты и геоданные — неизменяемое содержимое образа.
Обновления ПО внутри контейнера нет. Исправления безопасности выходят в новом
версионируемом образе: загрузите новый тег из Docker Hub `echodev7/mikrozia`,
пересоздайте контейнер с теми же монтированиями `/etc/x-ui` и `/root/cert` и
сохраняйте предыдущий образ до проверки нового. См.
[Обновление и удаление](/docs/guide/update-uninstall).
