Вся ваша конфигурация — входящие подключения, клиенты, настройки — хранится в
базе данных панели. Регулярно создавайте резервные копии, чтобы иметь возможность
восстановления или переноса.

## Что копировать

- **База данных** — по умолчанию SQLite в `/etc/x-ui/x-ui.db` (или ваша база
  данных PostgreSQL, если вы используете этот бэкенд).
- **Сертификаты** — всё, что находится в `/root/cert/` (или там, где вы храните
  сертификаты TLS).

## Ручное резервное копирование

Чтобы создать согласованную резервную копию SQLite, пока панель работает,
сформируйте текстовый SQL-дамп внутри контейнера:

```bash title="create a consistent SQLite backup"
x-ui migrate-db --dump /etc/x-ui/x-ui-backup-$(date +%F).sql
```

Дамп читает согласованный снимок базы данных, в том числе при активном режиме
WAL SQLite. Не копируйте `/etc/x-ui/x-ui.db` напрямую, пока контейнер работает.
Если нужен исходный файл `.db`, сначала остановите контейнер, а затем скопируйте
базу из постоянного хранилища RouterOS. Загрузки из веб-панели, экспорт для
междвижковой миграции (`.dump` / `.db`), а также резервные копии Telegram и
Discord сначала записываются во временный приватный файл в `/etc/x-ui` (или
`XUI_DB_FOLDER`) и передаются потоково; убедитесь, что на томе достаточно места
для временного файла.

Для восстановления SQL-дампа создайте новый файл базы данных; эта команда пишет
в отдельный файл и не изменяет рабочую базу. Затем остановите контейнер, замените
`/etc/x-ui/x-ui.db` новым файлом и запустите контейнер:

```bash
x-ui migrate-db --restore /etc/x-ui/x-ui-backup-YYYY-MM-DD.sql --out /etc/x-ui/x-ui-restored.db
```

CLI не перезаписывает существующий файл назначения. Перед заменой базы данных
исходным файлом `.db` остановите контейнер.

> Импорт через веб-панель (`POST /panel/api/server/importDB`) записывает файл потоково напрямую во временный приватный файл на постоянном томе `/etc/x-ui` (или `XUI_DB_FOLDER`) с ограничением по умолчанию **256 MiB** (`XUI_DB_IMPORT_MAX_MIB`, допустимый диапазон **32–2048 MiB**). Загрузки, превышающие этот предел, отклоняются с ошибкой **HTTP 413** (`Request Entity Too Large`). Увеличивайте `XUI_DB_IMPORT_MAX_MIB` только при наличии достаточного свободного места на томе `/etc/x-ui`; Mikrozia никогда не изменяет правила Firewall или NAT в RouterOS автоматически.

<Callout type="warn">
  По возможности восстанавливайте резервную копию на **той же мажорной версии**, с
  которой она была создана. При переходе между мажорными версиями дайте панели
  выполнить миграции, а не навязывайте старую схему.
</Callout>

## Автоматические бэкапы ботов (Telegram и Discord)

Если вы настроили [Telegram-бота](/docs/operations/telegram-bot) или [Discord-бота](/docs/operations/discord-bot), включите **`tgBotBackup`** или **`discordBotBackup`**, чтобы прикреплять резервную копию к периодическому отчёту (по расписанию `tgRunTime` / `discordRunTime`, по умолчанию ежедневно). Бот отправляет в чат или канал администратора как **базу данных**, так и **`config.json` Xray**, поэтому у вас всегда будет копия за пределами сервера. Администраторы также могут запросить резервную копию по требованию через меню бота Telegram или с помощью команды `!backup` в Discord.

## Дамп / восстановление SQLite

Команда `x-ui migrate-db` преобразует базу данных SQLite в обычный текстовый дамп
SQL и обратно (удобно для просмотра или переноса между машинами):

```bash
x-ui migrate-db --dump /etc/x-ui/x-ui.sql       # SQLite -> SQL text
x-ui migrate-db --restore /etc/x-ui/x-ui.sql --out /etc/x-ui/x-ui-restored.db
```

Для `--restore` обязателен `--out`, и CLI никогда не перезаписывает существующую базу данных. Интерактивное меню **Инструменты базы данных** сначала восстанавливает данные во временный файл и заменяет выбранный выходной файл только после успешного восстановления; при сбое прежний файл остается без изменений.

> Восстановление из текстового SQL-дампа SQLite (`x-ui migrate-db --restore` и загрузка `.sql`-дампа SQLite через `importDB`) выполняется потоково, по одному SQL-оператору без загрузки всего файла в оперативную память. Размер одного оператора по умолчанию ограничен **16 MiB** (`XUI_SQLITE_RESTORE_MAX_STATEMENT_MIB`, допустимый диапазон **1–256 MiB**). Увеличение этого параметра повышает потребление RAM на один оператор — увеличивайте его на контейнерах RouterOS только при наличии достаточного запаса памяти. Импорт бинарных файлов `.db` и дампов PostgreSQL не использует `XUI_SQLITE_RESTORE_MAX_STATEMENT_MIB` (общий размер загрузки по-прежнему регулируется отдельно через `XUI_DB_IMPORT_MAX_MIB`).

Чтобы перейти на PostgreSQL, смотрите раздел [База данных](/docs/reference/database).

> При использовании PostgreSQL резервное копирование (`.dump` через `pg_dump`) и восстановление (`pg_restore`) определяют живую схему по `search_path` для основных таблиц (`users`, `settings`, `inbounds`) на одном закреплённом соединении и строго ограничивают утилиты этой схемой (`--strict-names`, `--schema=...`). Разделение основных таблиц по разным схемам или попадание в системные схемы отклоняется.

> Перед заменой рабочей базы данных SQLite Mikrozia создаёт согласованный с WAL резервный снимок и записывает устойчивый маркер состояния в `XUI_DB_FOLDER`. При потере питания или сбое во время импорта следующий запуск автоматически восстановит транзакцию. **Не удаляйте** вручную каталоги `.mikrozia-sqlite-restore-*` или файл маркера `.mikrozia-sqlite-restore-state.json`; при повреждении маркера запуск безопасно остановится, сохранив журналы и артефакты без слепого удаления пользовательских данных.

## Безопасность резервного копирования и импорта PostgreSQL

PostgreSQL остаётся внешним и опциональным бэкендом — см. [База данных](/docs/reference/database). Клиентские утилиты PostgreSQL уже входят в образ; не устанавливайте `pg_dump` или `pg_restore` на хост RouterOS.

Перед разрушающим импортом в PostgreSQL (восстановление `.dump` или импорт файла SQLite в PostgreSQL) Mikrozia создаёт проверенный снимок перед импортом:

- Снимок размещается в приватном каталоге `.mikrozia-pg-restore-*` внутри `XUI_DB_FOLDER`; каталог имеет права `0700`, а файл `pre-import.dump` — `0600`.
- Импорт начинается только при объёме свободного места не менее примерно размера канонической схемы плюс 25% плюс 16 MiB.
- Перед любым изменением снимок проверяется через `pg_restore --list` и удаляется после успешного импорта.

Если импорт завершается ошибкой после фиксации (повторное открытие базы данных, восстановление настроек этого роутера, применение миграций данных панели или перезапуск Xray), Mikrozia выполняет точный откат: удаляются только объекты определённой канонической схемы, при этом сама схема, её владелец и ACL сохраняются, другие схемы не затрагиваются, снимок восстанавливается без `--clean`, пул соединений открывается заново, а Xray перезапускается. Если автоматический откат не удался, снимок сохраняется, а ошибка сообщает его путь для ручного восстановления; не удаляйте его, пока состояние базы данных не подтверждено.

Если панель или контейнер аварийно завершится во время импорта, проверенный снимок `.mikrozia-pg-restore-*` останется на месте. Не удаляйте его и не запускайте другой образ на изменённой схеме; проверьте базу данных и восстановите этот снимок вручную через `pg_restore`, прежде чем продолжать.

Параметр `keepHostSettings` в `POST /panel/api/server/importDB` управляет привязанными к хосту настройками, такими как `webPort`, `webBasePath`, пути к сертификатам, `panelGuid` и материал mTLS узла. При значении **true** текущие значения этого роутера применяются повторно после импорта; при **false** сохраняются значения из импортированных данных.

Учётные данные PostgreSQL никогда не попадают в журналы или вывод CLI. `PGPASSWORD` не поддерживается; утилиты получают временный `PGPASSFILE` с правами `0600`, а вывод ошибок/stderr редактируется (redact).

<Callout type="info">
  Каким бы методом вы ни пользовались, храните резервные копии **за пределами
  сервера** и периодически проверяйте восстановление — непроверенная резервная
  копия не является резервной копией.
</Callout>
