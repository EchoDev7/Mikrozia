Mikrozia слушает лишь несколько портов **внутри** контейнера. Проект никогда не
создаёт и не изменяет правила RouterOS для firewall, NAT, masquerade, port
forwarding, routing или access control, а образ не содержит `ufw`, `iptables` или
`nftables`.

## Порты внутри контейнера

| Порт (по умолчанию) | Назначение |
| ------------------- | ---------- |
| `2053` | Панель (настраивается в Panel Settings) |
| `2096` | Сервер подписок (если включён) |
| порты inbound | Каждый порт, назначенный inbound-подключению Xray |

Адрес контейнера в базовой схеме — `172.16.10.2`.

## Сетевая политика — ваша

Решите в RouterOS, как эти порты будут доступны:

- какой интерфейс или address list может обращаться к панели;
- будет ли и как порт inbound перенаправляться на `172.16.10.2`;
- как контейнер выходит в интернет;
- политика drop, rate limit и логирования.

Mikrozia документирует необходимые порты, но не автоматизирует эти шаги. Для
firewall, NAT и routing следуйте документации MikroTik по RouterOS.

<Callout type="warn">
  Перед применением ограничительной политики убедитесь, что управляющий доступ к
  самому RouterOS продолжает работать. Проверяйте из второй сессии, чтобы не
  заблокировать себя.
</Callout>

## Проверка изнутри

Если клиент не подключается, сначала убедитесь, что панель и Xray работают внутри
контейнера:

```text
/container/print detail where comment="[Mikrozia:container] Container"
/log/print follow-only where topics~"container"
```

Затем проверьте, что политика RouterOS действительно доставляет трафик на адрес и
порт контейнера. См. [Устранение неполадок](/docs/help/troubleshooting).
