تمام پیکربندی شما — ورودی‌ها، کلاینت‌ها و تنظیمات — در پایگاه‌داده‌ی پنل
قرار دارد. مرتب از آن پشتیبان بگیرید تا بتوانید بازیابی یا مهاجرت کنید.

## از چه چیزی پشتیبان بگیریم

- **پایگاه‌داده** — به‌صورت پیش‌فرض یک SQLite در `/etc/x-ui/x-ui.db` (یا پایگاه‌داده‌ی
  PostgreSQL شما اگر از آن backend استفاده می‌کنید).
- **گواهی‌ها** — هر چیزی که زیر `/root/cert/` (یا هر جایی که گواهی‌های TLS را نگه می‌دارید)
  قرار دارد.

## پشتیبان‌گیری دستی

برای تهیه‌ی یک نسخه‌ی پشتیبان سازگار از SQLite در حالی که پنل در حال اجراست، یک
دامپ متنی SQL از داخل کانتینر بسازید:

```text title="RouterOS: ورود به کانتینر در حال اجرا"
/container/shell [find where comment="[Mikrozia:container] Container"]
```

```bash title="Shell کانتینر: ساخت Backup سازگار SQLite"
x-ui migrate-db --dump /etc/x-ui/x-ui-backup-$(date +%F).sql
exit
```

این دامپ یک Snapshot سازگار از پایگاه‌داده می‌خواند، حتی زمانی که حالت WAL
SQLite فعال است. هنگام اجرای کانتینر، فایل `/etc/x-ui/x-ui.db` را مستقیماً کپی
نکنید. اگر به فایل خام `.db` نیاز دارید، ابتدا کانتینر را متوقف کنید و سپس فایل
را از Mount پایدار RouterOS کپی کنید. دانلود از پنل وب، خروجی مهاجرت بین‌موتوری
(`.dump` / `.db`)، Telegram و Discord ابتدا در یک فایل موقت خصوصی زیر `/etc/x-ui`
(یا `XUI_DB_FOLDER`) آماده و به‌صورت جریانی ارسال می‌شوند؛ فضای کافی برای فایل
موقت در Mount در نظر بگیرید.

برای آزمایش سالم‌بودن دامپ SQL، آن را در یک فایل پایگاه‌داده‌ی جدید بازسازی کنید؛
این دستور فایل جداگانه‌ای می‌سازد و پایگاه‌داده‌ی زنده را تغییر نمی‌دهد:

```bash
x-ui migrate-db --restore /etc/x-ui/x-ui-backup-YYYY-MM-DD.sql --out /etc/x-ui/x-ui-restored.db
```

CLI فایل مقصد موجود را بازنویسی نمی‌کند. پس از خروجی موفق، فایل SQL زیر
`containers/mikrozia/data/` در **WinBox → Files** قرار دارد؛ آن را روی یک دستگاه
دیگر دانلود کنید. فایل آزمایشی `x-ui-restored.db` را پس از بررسی حذف کنید.

برای **Restore واقعی**، فایل `.sql` را با **Panel Dashboard → Backup & Restore →
Restore** Upload کنید؛ جایگزینی از طریق پنل تراکنشی است، از دیتابیس زنده Snapshot
می‌گیرد و در خطا به دادهٔ قبلی برمی‌گردد. Restore واقعی را با rename/کپی دستی
`x-ui.db` انجام ندهید. پیش از آن یک dump تازه بگیرید، یک نشست مدیریت دوم باز
نگه دارید، و تا پایان پیام موفقیت Container را Restart یا متوقف نکنید.

> واردکردن پایگاه‌داده از طریق پنل وب (`POST /panel/api/server/importDB`) فایل را مستقیماً به‌صورت جریانی روی مانت پایدار `/etc/x-ui` (یا `XUI_DB_FOLDER`) با سقف پیش‌فرض **256 MiB** (`XUI_DB_IMPORT_MAX_MIB` در بازه مجاز **32 تا 2048 MiB**) Stage می‌کند. در صورت عبور حجم فایل از این سقف، درخواست با خطای **HTTP 413** (`Request Entity Too Large`) رد می‌شود. مقدار `XUI_DB_IMPORT_MAX_MIB` را تنها زمانی افزایش دهید که مانت `/etc/x-ui` فضای آزاد کافی داشته باشد؛ میکروزیا هرگز قوانین Firewall یا NAT روترOS را به‌صورت خودکار تغییر نمی‌دهد.

<Callout type="warn">
  هر وقت ممکن است، یک نسخه‌ی پشتیبان را روی **همان نسخه‌ی اصلی (major)** که از آن گرفته شده
  بازیابی کنید. در ارتقاهای میان‌نسخه‌ای اصلی، به‌جای تحمیل یک شِمای قدیمی، بگذارید پنل
  مهاجرت‌های خود را اجرا کند.
</Callout>

## پشتیبان‌گیری خودکار با ربات‌ها (Telegram و Discord)

اگر [ربات Telegram](/docs/operations/telegram-bot) یا [ربات Discord](/docs/operations/discord-bot) را پیکربندی کرده‌اید، گزینه‌ی **`tgBotBackup`** یا **`discordBotBackup`** را فعال کنید تا یک نسخه‌ی پشتیبان به گزارش دوره‌ای ضمیمه شود (بر اساس زمان‌بندی `tgRunTime` / `discordRunTime`، به‌صورت پیش‌فرض روزانه). ربات هم **پایگاه‌داده** و هم **`config.json` مربوط به Xray** را مستقیماً به چت یا کانال ادمین شما می‌فرستد، بنابراین همیشه یک نسخه‌ی خارج از سرور در اختیار دارید. ادمین‌ها همچنین می‌توانند به‌صورت درخواستی از منوی ربات Telegram یا با دستور `!backup` در Discord یک نسخه‌ی پشتیبان دریافت کنند.

## دامپ / بازیابی SQLite

دستور `x-ui migrate-db` پایگاه‌داده‌ی SQLite را به یک دامپ متنی SQL ساده و بالعکس تبدیل
می‌کند (برای بررسی یا انتقال میان دستگاه‌ها کاربردی است):

```bash
x-ui migrate-db --dump /etc/x-ui/x-ui.sql       # SQLite -> SQL text
x-ui migrate-db --restore /etc/x-ui/x-ui.sql --out /etc/x-ui/x-ui-restored.db
```

برای `--restore` گزینه‌ی `--out` الزامی است و CLI هرگز پایگاه‌داده‌ی موجود را بازنویسی نمی‌کند. منوی تعاملی **ابزارهای پایگاه‌داده** ابتدا در یک فایل موقت بازیابی می‌کند و تنها پس از موفقیت، فایل خروجی انتخاب‌شده را جایگزین می‌کند؛ بازیابی ناموفق فایل قبلی را بدون تغییر باقی می‌گذارد.

> بازیابی دامپ متنی SQLite (`x-ui migrate-db --restore` و آپلود دامپ متنی SQLite از طریق `importDB`) دستورها را به‌صورت جریانی و یکی‌یکی بدون بارگذاری کل فایل در حافظه اجرا می‌کند. هر دستور SQL به‌صورت پیش‌فرض به **16 MiB** محدود شده است (`XUI_SQLITE_RESTORE_MAX_STATEMENT_MIB` در بازه مجاز **1 تا 256 MiB**). افزایش این مقدار مصرف RAM به ازای هر دستور را بالا می‌برد؛ در کانتینرهای RouterOS تنها در صورت وجود حافظه کافی آن را افزایش دهید. واردکردن فایل باینری خام `.db` و دامپ PostgreSQL از `XUI_SQLITE_RESTORE_MAX_STATEMENT_MIB` استفاده نمی‌کنند (سقف کل حجم آپلود همچنان به‌صورت جداگانه با `XUI_DB_IMPORT_MAX_MIB` کنترل می‌شود).

برای مهاجرت به PostgreSQL، به [پایگاه‌داده](/docs/reference/database) مراجعه کنید.

> در بک‌اند PostgreSQL، بکاپ‌گیری (`.dump` با `pg_dump`) و بازیابی (`pg_restore`) پیش از اجرا Schema فعال انتخاب‌شده توسط `search_path` را برای جدول‌های اصلی (`users`، `settings`، `inbounds`) روی یک اتصال Pin‌شده استعلام کرده و ابزارها را با `--strict-names` و `--schema=...` دقیقاً به همان یک Schema محدود می‌کنند؛ پخش‌شدن جدول‌های اصلی بین چند Schema یا ارجاع به Schemaهای سیستمی رد می‌شود.

> پیش از جایگزینی پایگاه‌داده زنده SQLite، میکروزیا یک Snapshot سازگار با WAL می‌گیرد و یک State Marker پایدار زیر `XUI_DB_FOLDER` ثبت می‌کند. در صورت قطع برق یا Crash هنگام بازیابی، Startup بعدی تراکنش را به‌صورت خودکار بازیابی می‌کند. فایل‌ها و پوشه‌های `.mikrozia-sqlite-restore-*` یا State Marker را **هرگز به‌صورت دستی حذف نکنید**؛ در صورت خرابی Marker، Startup به‌شکل امن متوقف می‌شود تا Logها و Artifactها برای بررسی حفظ شوند و میکروزیا هرگز داده کاربران را برای بازیابی کورکورانه حذف نمی‌کند.

## ایمنی پشتیبان‌گیری و Import در PostgreSQL

PostgreSQL همچنان یک بک‌اند خارجی و اختیاری است — به [پایگاه‌داده](/docs/reference/database) مراجعه کنید. ابزارهای کلاینت PostgreSQL از قبل در ایمیج موجود هستند؛ `pg_dump` یا `pg_restore` را روی Host روترOS نصب نکنید.

پیش از هر Import مخرب در PostgreSQL (بازیابی یک `.dump` یا Import فایل SQLite به PostgreSQL)، میکروزیا یک Snapshot معتبر پیش از Import می‌سازد:

- Snapshot در یک پوشه خصوصی `.mikrozia-pg-restore-*` زیر `XUI_DB_FOLDER` قرار می‌گیرد؛ دسترسی پوشه `0700` و فایل `pre-import.dump` برابر `0600` است.
- Import تنها زمانی آغاز می‌شود که فضای آزاد حداقل به اندازه حجم Schema متعارف به‌علاوه ۲۵٪ و ۱۶ MiB باشد.
- Snapshot پیش از هر تغییری با `pg_restore --list` اعتبارسنجی می‌شود و پس از Import موفق حذف می‌گردد.

اگر Import پس از Commit شکست بخورد (بازکردن دوباره پایگاه‌داده، بازگرداندن تنظیمات این روتر، اعمال مهاجرت‌های داده پنل یا راه‌اندازی مجدد Xray)، میکروزیا به‌صورت دقیق Rollback می‌کند: تنها اشیای Schema متعارف تشخیص‌داده‌شده پاک می‌شوند و خود Schema، Owner و ACL آن حفظ می‌شود، سایر Schemaها دست‌نخورده می‌مانند، Snapshot بدون `--clean` بازیابی می‌شود، استخر اتصال دوباره باز شده و Xray مجدداً راه‌اندازی می‌شود. اگر این Rollback خودکار شکست بخورد، Snapshot نگه داشته می‌شود و خطا مسیر آن را برای بازیابی دستی گزارش می‌کند؛ تا زمان تأیید وضعیت پایگاه‌داده آن را حذف نکنید.

اگر پنل یا کانتینر هنگام Import به‌صورت ناگهانی متوقف شود، Snapshot معتبر `.mikrozia-pg-restore-*` در جای خود باقی می‌ماند. آن را حذف نکنید و ایمیج دیگری را روی Schema تغییرکرده اجرا نکنید؛ ابتدا وضعیت پایگاه‌داده را بررسی کنید و سپس آن Snapshot را به‌صورت دستی با `pg_restore` بازیابی کنید.

گزینه `keepHostSettings` در `POST /panel/api/server/importDB` تنظیمات وابسته به میزبان مانند `webPort`، `webBasePath`، مسیرهای گواهی، `panelGuid` و مواد mTLS نود را کنترل می‌کند. با مقدار **true**، مقادیر فعلی این روتر پس از Import دوباره اعمال می‌شوند؛ با مقدار **false**، مقادیر موجود در داده Importشده حفظ می‌شوند.

اعتبارنامه‌های PostgreSQL هرگز در Log یا خروجی CLI ظاهر نمی‌شوند. `PGPASSWORD` پشتیبانی نمی‌شود؛ ابزارها یک `PGPASSFILE` موقت با دسترسی `0600` دریافت می‌کنند و خروجی خطا/Stderr پاک‌سازی (Redact) می‌شود.

<Callout type="info">
  از هر روشی که استفاده می‌کنید، نسخه‌های پشتیبان را **خارج از سرور** نگه دارید و هرازگاهی
  یک بازیابی را آزمایش کنید — یک نسخه‌ی پشتیبانِ آزمایش‌نشده، پشتیبان به‌حساب نمی‌آید.
</Callout>
