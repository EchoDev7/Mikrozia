Mikrozia 将所有内容——入站、客户端、设置——都存储在数据库中。**SQLite** 是默认后端与新手推荐路径；**外部 PostgreSQL** 为可选的高级配置。Mikrozia 不在容器内安装或运行本地 PostgreSQL 服务器。

## SQLite（默认）

位于持久挂载 `/etc/x-ui/x-ui.db` 的单个文件。无需配置，适合 RouterOS Container 单节点部署。文件夹可通过 [`XUI_DB_FOLDER`](/docs/reference/env-vars#database) 配置。

## 外部 PostgreSQL（高级）

适合使用外部 PostgreSQL 服务器（支持 **15 至 18** 版本；在发布包含对应客户端的 Mikrozia 镜像前，不支持对 PostgreSQL 19+ 使用 `pg_dump` 备份）。

通过 RouterOS `/container/envs` 配置后端，支持 **URI**（`postgres://` 或 `postgresql://`）和 **Keyword/Value**（`host=... port=... user=... password=... dbname=...`）两种 DSN 格式：

```text
/container/envs/add list=mikrozia-env key=XUI_DB_TYPE value="postgres"
/container/envs/add list=mikrozia-env key=XUI_DB_DSN value="postgres://xui:<CHANGE_ME_PASSWORD>@db.example.internal:5432/xui?sslmode=verify-full&sslrootcert=/root/cert/pg-ca.crt"
```

### TLS、凭据与有界超时

- **TLS 证书：** 将 CA 与客户端证书放在持久挂载 `/root/cert` 下。推荐使用安全模式 `sslmode=verify-full`，且证书 SAN 必须与 `XUI_DB_DSN` 中的主机名一致。
- **不使用 `PGPASSWORD` 且不泄露密码：** Mikrozia 不会在 CLI 输出或日志中打印密码，也不支持 `PGPASSWORD`。`pg_dump` / `pg_restore` 会自动使用权限为 `0600` 的临时 `PGPASSFILE`，并在成功、失败或超时后立即删除。
- **有界超时：** 启动连接重试受总截止时间限制（总计 75 秒，单次尝试 10 秒），本地工具也强制执行超时限制（`pg_restore --list` / `--version`：15 秒，`pg_dump`：10 分钟，`pg_restore`：15 分钟）。
- **严格 Schema 范围：** 在运行 `pg_dump` 或 `pg_restore` 之前，Mikrozia 会在单个固定连接上解析 `search_path` 为核心表（`users`、`settings`、`inbounds`）选中的实际 Schema，并使用 `--strict-names` 和 `--schema=...` 严格限定为该单一 Schema；若核心表分散在多个 Schema 中或解析到系统 Schema，则会直接拒绝。

切换后端时，请使用更新后的 `envlist` 和相同的持久挂载（`/etc/x-ui` 与 `/root/cert`）重建容器，不要编辑 `/etc/conf.d/x-ui`。

使用 `XUI_DB_MAX_OPEN_CONNS` 和 `XUI_DB_MAX_IDLE_CONNS` 调优连接池。

<Callout type="info">
  官方镜像在构建时已内置 `pg_dump` 和 `pg_restore`（PostgreSQL 18 客户端）。运行时不存在 `apk add`、`apt install` 或 `x-ui pgclient`——请通过升级 Mikrozia 镜像来更新客户端工具。
</Callout>

### 已在 PostgreSQL 18 上实测

当前测试套件会连接真实的 PostgreSQL 18 服务器并使用 PostgreSQL 18 客户端工具运行，覆盖 URI 与 Keyword/Value DSN 初始化、规范 Schema 解析（包括含大写字母、空格、点和双引号的 Schema 标识符）、PostgreSQL 到 SQLite 导出、导入前的已验证快照、提交后的精确回滚，以及 `keepHostSettings` 的两种模式。这不改变上文所述的受支持服务器版本范围。

破坏性导入会先创建经过验证的导入前快照，并在失败时精确回滚；参见[备份与恢复](/docs/operations/backup-restore#postgresql-backup-and-import-safety)。

### 本地开发（`docker-compose.yml`）

`docker-compose.yml` 仅用于**本地开发与自动化测试**，不是 RouterOS Container 的生产安装路径。

## 从 SQLite 迁移到 PostgreSQL

<Callout type="warn">
  **不建议**直接在正在运行且持续写入的 SQLite 数据库文件上执行
  `x-ui migrate-db`，因为 Shell 不会停止容器中的面板进程，并发写入可能导致快照不一致。请先获取一致的
  SQLite 备份/快照（例如通过面板备份或在 RouterOS 上停止容器后复制），再通过 `--src` 对该快照执行迁移。
</Callout>

使用内置命令将一致的 SQLite 快照迁移到外部 PostgreSQL：

```bash
x-ui migrate-db --src /etc/x-ui/x-ui-snapshot.db --dsn "postgres://xui:<CHANGE_ME_PASSWORD>@db.example.internal:5432/xui?sslmode=verify-full&sslrootcert=/root/cert/pg-ca.crt"
```

然后在 RouterOS `/container/envs` 中设置 `XUI_DB_TYPE` 和 `XUI_DB_DSN`，并使用相同的持久挂载（`/etc/x-ui` 与 `/root/cert`）重建或替换容器。

<Callout type="info">
  源 SQLite 文件不会被改动——只有在你确认新后端正常工作后，才手动
  将其删除。
</Callout>

## 备份

无论使用哪种后端，都要定期备份——参见
